# Benchmarks

A standalone JMH project. It depends on the installed `eagerseq` artifact
and does not touch the library's own build.

```
mvn install                                   # in the repository root
cd bench
mvn package
java -jar target/benchmarks.jar               # full run, about 45 minutes
java -jar target/benchmarks.jar mapToList     # one benchmark
java -jar target/benchmarks.jar -f 1 -wi 2 -i 2 -w 300ms -r 300ms   # quick and noisy
```

The jar takes the usual JMH arguments (`-h` lists them). It adds the GC
profiler and a fixed 2g heap itself, and when the run finishes writes the
results as markdown to `RESULTS.md` in the working directory, or to the
path given by `-Dresults=...`. On a busy machine, pinning to one core
helps: `taskset -c 5 java -jar ...`.

The `eagerseq` version is a property in `pom.xml`; pass
`-Deagerseq.version=...` if it has moved on.

## What is measured

Each benchmark runs the same pipeline four ways:

- `SEQSTREAM` against `JDK` is the like-for-like comparison. The working
  budget is within a factor of 2, faster is a bonus.
- `SEQ` against `JDK` measures the cost of eagerness, i.e. an array per
  stage. Expect it to lose at large sizes. That is a design choice, not a
  regression.
- `LOOP` is a hand-written loop and is the floor.

The cases cover pipeline shapes rather than operators: map and filter
chains, buffering stages (`sorted`, `distinct`), short-circuiting
(`anyMatch`, `takeWhile`), `flatMap`, and each source kind (array,
collection, iterator). Size 10 is there for per-pipeline fixed cost, which
is what matters most for eager `Seq` in practice.

Allocation (B/op) is deterministic and so far more stable than time on a
noisy machine. When in doubt, read that column first.

## Results

Results are for a human to read, not for CI to assert on. JMH on a shared
runner is too noisy for a pass/fail ratio. CI only compiles this project so
it cannot silently rot when the API changes.

`RESULTS.md` is regenerated by hand when `Sources` changes materially.
