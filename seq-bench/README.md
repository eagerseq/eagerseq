# Benchmarks

This JMH harness is part of the Maven reactor when Maven runs on JDK 17 or
newer. Build it and its current `seq` dependency from the repository root:

```
mvn -pl :seq-bench -am package
cd seq-bench
java -jar target/benchmarks.jar               # full run, about 45 minutes
java -jar target/benchmarks.jar mapToList     # one benchmark
java -jar target/benchmarks.jar -f 1 -wi 2 -i 2 -w 300ms -r 300ms   # quick and noisy
```

The default is size 1,000, two forks, three one-second warmup iterations
and three one-second measurement iterations. All are ordinary JMH options;
for example, add `-p size=10,1000,100000` for a size sweep.

The jar takes the usual JMH arguments (`-h` lists them). It adds the GC
profiler and a fixed 2g heap itself, and when the run finishes writes the
results as markdown to `RESULTS.md` in the working directory, or to the
path given by `-Dresults=...`. On a busy machine, pinning to one core
helps: `taskset -c 5 java -jar ...`.

The benchmark normally uses the `seq` artifact from the same reactor. To
compare with an installed or published release, select only the benchmark and
override the dependency version; `-am` would not build the current library in
this case because its version does not match the dependency:

```
mvn -pl :seq-bench -Dseq.version=0.6.0 package
```

## What is measured

There are two benchmark classes.

`PipelineBench` covers pipeline shapes with four implementations. `OperationBench`
covers many operators with two, `SeqStream` against the equivalent JDK
`Stream`, and is the one to use when looking for divergences. Its cases
are pairs of methods, `name_seq` and `name_jdk`; setup pairs them by
reflection and compares their results, so a case that does not measure
the same work fails before it is timed.

A full run writes separate sections for the two classes: the `PipelineBench`
tables retain all four implementations, while `OperationBench` is shown as
JDK/SeqStream ratios.

Two rules the cases follow, both learned the hard way:

- Never drain a pipeline with `count()`. On a sized source the JDK
  answers from the size and skips the pipeline, side effects included.
- At 100,000 elements, warm up for seconds rather than milliseconds, or
  the numbers measure the JIT rather than the library.

`PipelineBench` runs the same pipeline four ways:

- `SEQSTREAM` against `JDK` is the like-for-like comparison. The working
  budget is within a factor of 2, faster is a bonus.
- `SEQ` against `JDK` measures the cost of eagerness, i.e. an array per
  stage. Expect it to lose at large sizes. That is a design choice, not a
  regression.
- `LOOP` is a hand-written loop and is the floor.

The cases cover pipeline shapes rather than operators: map and filter
chains, buffering stages (`sorted`, `distinct`), short-circuiting
(`anyMatch`, `takeWhile`), `flatMap`, and each source kind (array,
collection, iterator). Size 10 is there for per-pipeline fixed cost, which
is what matters most for eager `Seq` in practice.

Allocation (B/op) is deterministic and so far more stable than time on a
noisy machine. When in doubt, read that column first.

## Results

Results are for a human to read, not for CI to assert on. JMH on a shared
runner is too noisy for a pass/fail ratio. CI packages this project but does
not execute it, so the source cannot silently rot when the API changes.

`RESULTS.md` holds the current findings and the reasoning behind them. It
is regenerated by hand when `Sources` changes materially. Ratios in it come
from 3-fork runs and carry an error column; a row with more than about 10%
error is noise, not a finding.
